OmniTrace AI 어시스턴트

OpenTelemetry 기반 온프레미스 APM 플랫폼 OmniTrace에서 AI 어시스턴트를 만들었습니다. 운영자가 자연어로 물으면 실제 데이터로 답을 받습니다. 외부 API를 쓸 수 없는 폐쇄망 고객 환경이라 자체 호스팅한 Gemma 4를 씁니다. 그 위에 RAG 문서 라이브러리와 채점 시스템까지 직접 구축했습니다.

2026.02 ~ 현재 LLM 레이어 담당 팀 프로젝트 고객사 POC 진행

무엇을 만들었나

APM 화면은 데이터가 많지만 원하는 숫자를 찾으려면 대시보드와 쿼리를 직접 다뤄야 합니다. AI 어시스턴트는 "지난주 크래시가 많았던 화면이 어디야?" 같은 질문을 받아 의도를 분류하고 ClickHouse SQL 조회, 지식베이스 검색, 대시보드 위젯 생성 중 맞는 도구로 답합니다.

OTel Collector와 ClickHouse 수집 인프라는 팀과 함께 구축했고 그 위의 LLM 레이어(의도 라우팅, Text-to-SQL, 근거 주입, RAG 문서 라이브러리, 채점 시스템, PII 마스킹)를 맡았습니다.

RAG 문서 라이브러리

모델은 제품의 스키마와 지표 정의를 모르면 그럴듯한 SQL과 설명을 지어냅니다. 그래서 답변 근거로 넣을 지식 카드 59장을 같은 형식으로 썼습니다. 관리 화면에서 고치면 바로 검색에 반영되게 했습니다.

카드 종류수쓰임
SQL 예시32장크래시, 프리즈, 세션 같은 지표별 질문과 SQL 쌍. Text-to-SQL의 few-shot으로 들어갑니다.
런북15장장애 대응과 보안 점검 절차. 어떻게 대응할지 묻는 질문의 근거가 됩니다.
지표 정의12장p95, Apdex, crash-free처럼 운영자가 묻는 용어의 정의입니다.
  • 하이브리드 검색BGE-M3 임베딩과 BM25를 Qdrant에서 RRF로 합칩니다. 벡터 검색을 쓸 수 없을 때는 키워드 검색으로 넘어가서 검색 장애가 답변 전체를 막지 않습니다.
  • 현장 용어 연결사용자가 실제로 쓰는 표현을 카드에 별칭으로 넣어 공식 용어를 몰라도 맞는 카드를 찾게 했습니다.
  • 채점 결과로 보강QA와 채점에서 틀린 질문을 근거로 빠진 카드를 찾아 추가했습니다.

채점 시스템

프롬프트나 도구를 바꿀 때마다 좋아졌는지 나빠졌는지를 숫자로 보려고 채점 시스템을 직접 만들었습니다. 답변이 실제 근거에 기반했는지 보는 항목의 통과율은 93.4%였습니다. 처음 만든 골든셋은 단일 질문 SQL 생성에서 금방 100%가 나와 더 이상 차이를 보여 주지 못했습니다. 그래서 멀티턴 대화, 지시어가 섞인 질문, 여러 의도가 한 번에 들어간 질문으로 평가셋을 넓혔습니다.

  1. 검증 실행질문 뱅크와 고정 대화 흐름을 실제 모델로 실행
  2. 자동 채점정해진 규칙 6개와 LLM 채점기로 축별 통과율 산출
  3. 채점기 보정축마다 사람이 3~5개만 라벨해 채점기가 믿을 만한지 확인
  4. 회귀 확인수정 전후 결과를 비교해 나빠진 항목을 찾고 다시 고침

같은 답변을 다시 채점하면 점수가 흔들리는 문제는 채점 결과 캐시와 라우팅 결정성으로 줄였습니다. 품질 회귀 감지와 라벨링 화면도 함께 만들었습니다.

틀린 답을 막는 장치

  • 조회 결과가 없으면 지어내지 않기SQL 결과가 0건이면 기간을 넓혀 한 번 다시 조회하고 그래도 없으면 "데이터 없음"을 근거로 답합니다. 행이 없는데 숫자를 만들어 내던 답변을 이 경로로 막았습니다.
  • 답변 속 숫자 대조답변에 나온 숫자가 실제 조회 결과에 있는지 검사하는 가드를 넣었습니다.
  • 도메인 가드레일APM과 관계없는 질문, 데이터 삭제·변경 요청은 3단계로 걸러 거절합니다.
  • 멀티턴 맥락"그 서비스", "아까 거"처럼 앞 대화를 가리키는 말을 풀고 직전 조회를 이어받아 다음 SQL을 만듭니다.
  • 개인정보 마스킹대화 로그를 저장할 때 개인정보를 가려서 ClickHouse에 남깁니다.

AI 어시스턴트 개발 내용

  • 전용 화면과 스트리밍어시스턴트 전용 페이지를 만들었습니다. 다른 메뉴로 이동해도 답변 스트리밍이 끊기지 않게 했습니다. 대화는 사용자별로 PostgreSQL에 저장하고 답변 아래에는 결과 표(30행까지와 총건수)와 좋아요·싫어요 피드백을 붙였습니다.
  • 구조화 라우터LLM이 의도와 조회 조건을 JSON으로 함께 내도록 라우터를 바꿨습니다. 조건이 모호하면 되묻고 형식이 깨지면 기존 분류기로 넘어갑니다. 답변을 실행하지 않고 라우팅 결과만 확인하는 API도 열어 평가에 썼습니다.
  • SQL 생성LLM이 먼저 SQL을 짜고 EXPLAIN으로 검증한 뒤 실패하면 미리 만든 템플릿으로 넘어갑니다. "X 초과 목록"처럼 임계값을 묻는 질문에는 근거 수치 컬럼이 함께 나오게 규칙을 넣었습니다.
  • 위젯과 대시보드 생성질문에 맞는 출력 방식을 자동으로 고르고 여러 위젯을 대시보드로 묶어 줍니다. 비슷한 대시보드가 이미 있으면 RAG로 찾아 거기에 추가하도록 권합니다. 위젯을 만들 때 실제 스키마와 지식 카드를 근거로 넣어 없는 컬럼을 쓰지 않게 했습니다.
  • 복합 질문한 문장에 여러 의도가 있으면 나눠서 순서대로 답합니다.

AI 옵저빌리티

어시스턴트의 라우팅, SQL 생성, 답변 단계를 gen_ai 스팬으로 내보내 OmniTrace에서 직접 추적합니다. 질문과 답변은 ClickHouse에 압축해 90일 보관하고, 분석 화면에서 사용자별 이용 내역을 볼 수 있습니다.

세션 리플레이

사용자가 그 순간 본 앱 화면을 시간축으로 재생하고 같은 trace_id로 백엔드 호출과 나란히 봅니다. "API가 3초 걸렸을 때 사용자는 어떤 화면이었나"를 한 화면에서 확인할 수 있습니다. 풀스크린샷 대신 화면을 노드 트리로 재구성해 앱과 네트워크 부담을 줄이고 개인정보 노출을 막았습니다.

  1. SDK 캡처화면 뷰 트리와 스타일을 수집
  2. 증분 전송키프레임과 바뀐 노드만 전송
  3. 서버 재구성조회할 때 각 시점의 전체 화면을 복원
  4. 플레이어 재생이벤트 타임라인과 함께 재생
  5. 트레이스 연결재생 중 이벤트에서 트레이스로 이동
  • 플레이어스크러버, 이벤트 마커, 탭 표시가 있는 재생 화면을 만들었습니다. 특정 시점의 프레임을 계산하는 재생 엔진은 순수 함수로 분리해 테스트부터 작성했습니다.
  • 통합 세션 화면이슈가 있는 세션을 먼저 보여 주는 목록, 스크럽과 동기화된 이벤트 타임라인, 트레이스 드릴다운 드로어를 한 화면으로 묶었습니다.
  • 어느 앱이든 같은 렌더러처음에는 특정 앱의 디자인 값을 넣었는데, 다른 고객 앱에는 맞지 않아 제품 구조로 쓸 수 없었습니다. 지금 렌더러는 SDK가 캡처한 색과 글꼴을 그대로 그리고 없으면 중립 기본값을 씁니다. 스타일이 빠진 노드는 위치와 크기로 역할을 추정하고 글자색은 배경 밝기로 정합니다.
  • 마스킹 정책모든 노드를 가리면 회색 박스만 보여 쓸모가 없었습니다. 입력 필드와 지정한 민감 요소만 가리는 방식으로 바꾸고 가린 노드의 텍스트는 서버에서 한 번 더 비웁니다.
  • 전송량 절감전체 뷰 트리를 매번 보내던 것을 키프레임과 증분으로 바꿨습니다. 반복 이미지는 한 번만 보내고 화면 밖 노드는 그리지 않습니다. 픽셀 이미지를 전혀 보내지 않는 와이어프레임 모드도 넣었습니다.

그 밖에 맡은 일

  • 모바일 RUM모바일 SDK 수집 데이터를 세션 → 화면 → 액션 트리로 보여 주고 앱 요청과 백엔드 요청을 하나의 트레이스 워터폴로 이어 붙였습니다.
  • 긴 대화 활용256K 컨텍스트에 맞춰 대화 기록을 5턴에서 24턴까지 넣도록 늘리고 라우터는 최근 8턴만 보도록 나눴습니다. 호출 설정 8가지는 관리 화면에서 재시작 없이 바꿀 수 있습니다.
  • 이상 탐지3계층 이상 탐지 엔진 중 z-score 레이어를 구현했습니다.
  • 배포팀이 구성한 Docker Compose 환경에서 바뀐 서비스만 다시 배포하는 CI/CD 로직, 서버 배포 가이드, 로그 로테이션, ClickHouse 디스크 이전을 맡았고 HAProxy Collector 이중화 구성에 참여했습니다.
